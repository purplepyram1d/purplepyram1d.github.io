Repeated failed logins on a web portal

Six failed logins hit the FakeCorp portal from one workstation in under two minutes. I traced the alert back to its source, matched it to a planned login test and closed it in 25 minutes.

Affected host
SRV01
Detection
Wazuh rule 100343
Assessment
Expected Test Activity
Closed
Oct 6, 2026

  1. Alert

    Wazuh rule 100343 fired at level 10: six failed portal logins from the same workstation within 120 seconds. LabWatch opened the incident automatically.

  2. Investigation

    I pulled the portal's authentication log and the matching Wazuh and Splunk events, then compared the source address, accounts, failure sequence and timestamps across all three.

  3. Finding

    Every failure came from WS02 during a login test I ran myself. The single-failure rule fired first, then the threshold rule escalated the pattern into an incident, exactly as the two rules are meant to work together.

  4. Resolution

    I classified the incident as Expected Test Activity and closed it. No containment was needed.

In the wild

Password guessing, password spraying and credential stuffing against login pages are some of the most common alerts a SOC handles. The triage questions are the same every time: one source or many, one account or many, how fast, and did any attempt succeed.

SQL injection login bypass

A login to the FakeCorp portal succeeded with SQL injection in the email field. I confirmed the bypass was real, scoped the impact to one web application and closed the incident the same morning.

Affected host
SRV01
Detection
Wazuh rule 100345
Assessment
Expected Test Activity
Closed
Oct 6, 2026

  1. Alert

    Wazuh rule 100345 fired at level 12: a successful portal login whose email field contained SQL syntax.

  2. Investigation

    I compared the application's auth.log with the Wazuh and Splunk events, checking the submitted input against the real authentication result instead of trusting the HTTP response code.

  3. Finding

    The injection worked: the application logged a successful login. It was my own test against a deliberately vulnerable lab application, and the impact stopped at the portal. Active Directory and the other services on the server were not involved.

  4. Resolution

    I classified the incident as Expected Test Activity and closed it. The detection caught the exact case that matters most, an injection attempt that succeeded.

In the wild

Encoded PowerShell on a workstation

An encoded PowerShell command ran on WS01. I decoded it safely, traced it to a scheduled health check, found out why the check was failing and fixed it.

Affected host
WS01
Detection
Wazuh rule 92057
Assessment
Benign True Positive
Closed
Oct 15, 2026

  1. Alert

    Wazuh rule 92057 flagged an encoded PowerShell child process on WS01, raised from a Sysmon process-creation event.

  2. Investigation

    I decoded the command as text without executing it. It was an availability probe, launched by a scheduled task running as LOCAL SERVICE.

  3. Root cause

    The task was authorized, but its report showed the HTTPS request failing. The probe was pointed at an IP address instead of the service hostname.

  4. Fix

    I changed only the endpoint to the hostname and reran the same task under the same low-privilege account. It reached the service, got an HTTP 401 back and exited with result 0.

  5. Resolution

    I closed the incident as a Benign True Positive: the detection was correct, and the activity had an authorized purpose.

In the wild

Encoded PowerShell is a staple of malware loaders and hands-on-keyboard attackers because it hides the command from a quick look. Legitimate admin tooling uses it too, so an analyst has to decode it, find what launched it and decide whether it belongs.

Scheduled task running a script interpreter

A new scheduled task was registered on WS01 to run a script. I traced it to a legitimate queue job that was failing, found an explicit NTFS deny behind the failure and repaired it without elevating the account.

Affected host
WS01
Detection
Wazuh rule 100277
Assessment
Benign True Positive
Closed
Oct 15, 2026

  1. Alert

    Wazuh rule 100277 flagged a scheduled task that invokes a script interpreter, raised from Windows Security Event ID 4698 (scheduled task created).

  2. Investigation

    I traced the task to a local queue-processing script running as LOCAL SERVICE and compared who created the task with the account it runs as. Its report showed it could read its input but could not write its output.

  3. Root cause

    The output folder had an explicit Write deny for LOCAL SERVICE, which overrode the Modify permission the account inherited.

  4. Fix

    I removed only that deny entry and reran the original task as the same account. It wrote the expected summary and returned result 0, and the input file's hash was unchanged.

  5. Resolution

    I closed the incident as a Benign True Positive: the task registration was real and authorized, and the fault was a permission defect.

In the wild

Scheduled tasks are one of the most common ways attackers keep access and run code on Windows, which is why Event ID 4698 is worth alerting on. Most new tasks turn out to be legitimate, so the analyst checks who created it, what it runs and which account runs it.
